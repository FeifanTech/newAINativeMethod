# Java 企业级应用 · 架构与编码检查清单

> 本清单面向 **Java 企业级应用**（典型技术栈：Spring Boot + JPA/MyBatis + 消息中间件 + Redis + K8s）。  
> 供架构评审、设计评审、Code Review 时**逐项审查并给出结论**（满足 / 不满足 / 风险 + 建议）。  
> 若项目技术栈非 Java/Spring，可仅作参考或跳过；本仓其他原则与 Skills 仍为语言无关。

---

## 一、架构设计检查清单

评审时请按维度逐项给出：**现状**（简述）、**结论**（满足 / 不满足 / 风险）、**建议**（简短可执行）。

### 1.1 分层与边界

| 检查项 | 说明 |
|--------|------|
| 是否明确分层 | Controller / Application(Service) / Domain / Infrastructure 等层次是否清晰？ |
| 是否避免跨层直连 | 是否避免 Controller 直连 Repository、跨层调用乱穿？ |
| Service 是否按业务边界拆分 | Service 是否按业务域/限界上下文拆分，而非按技术栈或模块名堆在一起？ |
| 富领域模型场景 | 订单、账务等复杂业务是否有 Domain 层聚合根，而非所有逻辑塞在 Service 里？ |

### 1.2 事务与一致性

| 检查项 | 说明 |
|--------|------|
| 事务边界是否明确 | 哪些操作需要 ACID 事务？事务边界是否标明（如 @Transactional 放在哪一层）？ |
| 跨服务一致性策略 | 跨服务是否明确采用 Saga / 事件驱动 / 补偿，而非依赖「全局事务」假设？ |
| 读写分离与缓存 | 读写分离或缓存（如 Redis）场景是否明确 eventual consistency 策略与缓存过期/更新策略？ |

### 1.3 错误处理与失败模式

| 检查项 | 说明 |
|--------|------|
| 异常分类 | 是否区分「预期异常」与「不可预期异常」的处理方式？ |
| 外部依赖失败策略 | 第三方服务、消息中间件、文件存储等出错时的降级、熔断、限流策略？ |
| 重试、超时、幂等 | 是否规划了重试策略、超时配置、幂等机制（特别是写操作与消息消费）？ |

### 1.4 性能与容量规划

| 检查项 | 说明 |
|--------|------|
| 核心路径估算 | 是否对核心路径的 QPS/TPS、批处理/大查询做了估算或假设？ |
| 分页与批量 | 是否预留分页、游标、批量接口，而非一次性全量拉取？ |
| N+1 与大对象 | 是否识别潜在 N+1 查询、大对象序列化问题（典型如 JPA + JSON）？ |

### 1.5 可观测性（Observability）

| 检查项 | 说明 |
|--------|------|
| 日志 | 关键业务链路是否有统一 traceId/spanId？是否约定 log 格式与等级？ |
| 指标 | 是否为关键服务/接口设计基础指标（请求量、错误率、延迟、队列长度等）？ |
| 链路追踪 | 是否考虑接入 OpenTelemetry / Zipkin / Jaeger 等？ |

### 1.6 安全与多租户

| 检查项 | 说明 |
|--------|------|
| 鉴权模型 | 鉴权模型是否清楚（RBAC、ABAC 或更简单的角色权限）？ |
| 多租户隔离 | 是否考虑跨租户数据访问隔离（如 tenantId）？ |
| 敏感数据 | 手机号、证件号等敏感字段是否有脱敏/加密策略？ |
| 上传/下载 | 上传/下载接口是否有大小、类型限制与防注入思路？ |

### 1.7 配置与环境

| 检查项 | 说明 |
|--------|------|
| 配置集中管理 | 配置是否集中管理（如 Spring Cloud Config / Nacos / K8s ConfigMap/Secret），而非写死在代码或本地配置文件？ |
| 环境区分 | 是否区分 dev/test/staging/prod 的配置与限流策略？ |

### 1.8 Java 企业级默认偏好（参考）

- **技术栈假设**：Spring Boot + JPA/MyBatis + 消息中间件（Kafka/RabbitMQ）+ Redis + K8s。
- **架构风格**：业务简单时经典三层 + 模块化；业务复杂时 DDD 分层 + 有限领域服务 + 聚合根；避免过度微服务，慎重切分服务边界。
- **接口设计**：REST API 建议统一响应 envelope（code / message / data）；明确错误码规范与异常映射；幂等接口建议使用幂等键、乐观锁或租约机制。

## 二、编码与实现检查清单

Code Review 或实现建议时请按维度逐项给出：**现状**、**结论**（满足 / 不满足 / 风险）、**建议**。

### 2.1 包结构与命名

| 检查项 | 说明 |
|--------|------|
| 包约定 | 是否遵循 controller/api、service、domain、repository、config、client（调用外部服务）等包约定？ |
| 类命名职责清晰 | 是否避免含混命名（如 OrderManager / OrderService / OrderHelper），而用具体职责（如 OrderApplicationService / OrderDomainService）？ |

### 2.2 空指针与参数校验

| 检查项 | 说明 |
|--------|------|
| 空值处理 | 是否少用裸 null 判空，可选用 Objects.requireNonNull、校验框架、Optional（不滥用）？ |
| 对外接口校验 | Controller 层入参是否有 Bean 校验（Jakarta Validation）？ |

### 2.3 异常与返回值

| 检查项 | 说明 |
|--------|------|
| Service 层异常 | Service 层是否避免大面积 throws Exception？是否区分业务异常（Checked/自定义 Runtime）与系统异常？ |
| 失败反馈 | 是否不吞日志并返回模糊「失败」，而是记录上下文或将失败原因显式暴露到上层（脱敏后）？ |

### 2.4 日志实践

| 检查项 | 说明 |
|--------|------|
| 结构化日志 | 是否使用结构化日志（placeholder + 参数，而非字符串拼接）？ |
| 核心链路 | 入口、外部调用、异常、重要状态变迁是否有日志？ |
| 禁止大对象全量 | 是否禁止打印大对象全量（如完整请求体、响应体、大列表）？ |

### 2.5 性能与资源管理

| 检查项 | 说明 |
|--------|------|
| 循环内开销 | 是否避免在循环中频繁创建对象、发 SQL、发 RPC？ |
| 集合与流式 | 是否注意集合使用、流式操作的性能开销？ |
| 资源释放 | 文件/网络连接是否使用 try-with-resources 或明确关闭？ |

### 2.6 安全相关编码

| 检查项 | 说明 |
|--------|------|
| SQL 安全 | SQL 构造是否使用参数绑定，禁止字符串拼接拼 SQL？ |
| 日志不输出敏感信息 | 是否禁止在日志中输出用户密码、token、隐私数据？ |
| 外部输入校验 | 对外部输入（HTTP 参数、消息体）是否做类型与范围校验？ |
| 序列化安全 | 序列化/反序列化是否避免不安全类型（按团队约定）？ |

### 2.7 并发与共享状态

| 检查项 | 说明 |
|--------|------|
| Spring Bean 与静态变量 | 是否禁止在 Spring Bean 中用未经保护的可变静态变量共享状态？ |
| 并发与锁 | 并发集合、锁的使用是否说明意图，避免「隐形临界区」？ |
| 异步与线程池 | 异步/线程池是否考虑队列大小、拒绝策略？ |

### 2.8 编码风格与复杂度

| 检查项 | 说明 |
|--------|------|
| 统一 code style | 是否遵循团队/公司 code style（如 Google/Alibaba 等风格）？ |
| 方法/类/圈复杂度 | 是否控制方法长度、类大小、圈复杂度（如 Controller 方法尽量薄，复杂逻辑下沉 Service/Domain）？ |

## 三、输出格式建议

评审或 Code Review 时，**每个维度/每条检查项必须给出结论**，不能只罗列问题或原则。建议格式：

- **维度**：如「分层与边界」
- **现状**：1～2 句描述当前设计或代码情况
- **结论**：满足 / 不满足 / 风险（需改进）
- **建议**：简短可执行的一两句话

示例：

```text
维度：分层与边界
现状：OrderController 直接注入 OrderRepository 并调用 save。
结论：不满足
建议：将写操作经 OrderApplicationService 编排，Repository 仅由 Application 或 Infrastructure 层使用。
```
