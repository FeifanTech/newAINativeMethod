# TypeScript/TS 企业级应用 · 架构与编码检查清单

> 本清单面向 **TypeScript/TS 企业级应用**（典型技术栈：Node/Nest/Next + Prisma/TypeORM + Redis + K8s）。  
> 供架构评审、设计评审、Code Review 时**逐项审查并给出结论**（满足 / 不满足 / 风险 + 建议）。  
> 若项目技术栈非 TypeScript/Node，可仅作参考或跳过；本仓其他原则与 Skills 仍为语言无关。

---

## 一、架构设计检查清单

评审时请按维度逐项给出：**现状**（简述）、**结论**（满足 / 不满足 / 风险）、**建议**（简短可执行）。

### 1.1 分层与边界

| 检查项 | 说明 |
|--------|------|
| 是否明确分层 | Controller/Route、Application(Service)、Domain、Infrastructure(Repository/Client) 等层次是否清晰？ |
| 是否避免跨层直连 | 是否避免 Controller 直连 Repository/ORM、跨层调用乱穿？ |
| Service 是否按业务边界拆分 | Service 是否按业务域/限界上下文拆分，而非按技术栈或模块名堆在一起？ |
| 富领域模型场景 | 订单、账务等复杂业务是否有 Domain 层聚合/实体，而非所有逻辑塞在 Service 里？ |

### 1.2 事务与一致性

| 检查项 | 说明 |
|--------|------|
| 事务边界是否明确 | 哪些操作需要 ACID 事务？事务边界是否标明（如 Prisma $transaction、TypeORM DataSource）？ |
| 跨服务一致性策略 | 跨服务是否明确采用 Saga / 事件驱动 / 补偿，而非依赖「全局事务」假设？ |
| 读写分离与缓存 | 读写分离或缓存（如 Redis）场景是否明确 eventual consistency 策略与缓存过期/更新策略？ |

### 1.3 错误处理与失败模式

| 检查项 | 说明 |
|--------|------|
| 异常/错误分类 | 是否区分「预期错误」（业务错误）与「不可预期错误」的处理方式？ |
| 外部依赖失败策略 | 第三方服务、消息队列、文件存储等出错时的降级、熔断、限流策略？ |
| 重试、超时、幂等 | 是否规划了重试策略、超时配置、幂等机制（特别是写操作与消息消费）？ |

### 1.4 性能与容量规划

| 检查项 | 说明 |
|--------|------|
| 核心路径估算 | 是否对核心路径的 QPS/TPS、批处理/大查询做了估算或假设？ |
| 分页与批量 | 是否预留分页、游标、批量接口，而非一次性全量拉取？ |
| N+1 与大对象 | 是否识别潜在 N+1 查询、大对象序列化问题（典型如 ORM + JSON）？ |
| 事件循环与阻塞 | 是否避免在 Node 主线程中长时间同步阻塞（CPU 密集或大 JSON 解析）？ |

### 1.5 可观测性（Observability）

| 检查项 | 说明 |
|--------|------|
| 日志 | 关键业务链路是否有统一 traceId/requestId？是否约定 log 格式与等级？ |
| 指标 | 是否为关键服务/接口设计基础指标（请求量、错误率、延迟、队列长度等）？ |
| 链路追踪 | 是否考虑接入 OpenTelemetry / Jaeger 等？ |

### 1.6 安全与多租户

| 检查项 | 说明 |
|--------|------|
| 鉴权模型 | 鉴权模型是否清楚（RBAC、ABAC 或 JWT/OAuth2 等）？ |
| 多租户隔离 | 是否考虑跨租户数据访问隔离（如 tenantId）？ |
| 敏感数据 | 手机号、证件号等敏感字段是否有脱敏/加密策略？ |
| 上传/下载 | 上传/下载接口是否有大小、类型限制与防注入思路？ |

### 1.7 配置与环境

| 检查项 | 说明 |
|--------|------|
| 配置集中管理 | 配置是否集中管理（如环境变量 / K8s ConfigMap/Secret），而非写死在代码或 .env 提交到仓库？ |
| 环境区分 | 是否区分 dev/test/staging/prod 的配置与限流策略？ |

### 1.8 TypeScript/Node 企业级默认偏好（参考）

- **技术栈假设**：Node/Nest/Next + Prisma/TypeORM + Redis + 消息队列 + K8s。
- **架构风格**：业务简单时分层 + 模块化；业务复杂时 DDD 分层 + 有限领域服务；避免过度微服务。
- **接口设计**：REST API 建议统一响应 envelope（code / message / data）；明确错误码与异常映射；幂等接口建议使用幂等键或租约机制。

## 二、编码与实现检查清单

Code Review 或实现建议时请按维度逐项给出：**现状**、**结论**（满足 / 不满足 / 风险）、**建议**。

### 2.1 模块结构与命名

| 检查项 | 说明 |
|--------|------|
| 模块约定 | 是否遵循 controller、service、domain、repository、config、client 等目录约定（或项目约定）？ |
| 命名职责清晰 | 是否避免含混命名（如 OrderManager / OrderHelper），而用具体职责（如 OrderApplicationService / OrderDomainService）？ |

### 2.2 类型与参数校验

| 检查项 | 说明 |
|--------|------|
| 类型使用 | 是否对公共接口、入参、返回值使用 TypeScript 类型/接口，避免 any 泛滥？ |
| 对外接口校验 | API 层入参是否有校验（如 class-validator、Zod、Joi）？ |

### 2.3 异常与返回值

| 检查项 | 说明 |
|--------|------|
| 错误分层 | Service 层是否区分业务错误与系统错误（如自定义 Error 子类或 Result 类型）？ |
| 失败反馈 | 是否不吞异常并返回模糊「失败」，而是记录上下文或将失败原因显式暴露到上层（脱敏后）？ |

### 2.4 日志实践

| 检查项 | 说明 |
|--------|------|
| 结构化日志 | 是否使用结构化日志（如 pino / winston 的 JSON 格式），而非字符串拼接？ |
| 核心链路 | 入口、外部调用、异常、重要状态变迁是否有日志？ |
| 禁止大对象全量 | 是否禁止打印大对象全量（如完整请求体、大数组）？ |

### 2.5 性能与资源管理

| 检查项 | 说明 |
|--------|------|
| 循环内开销 | 是否避免在循环中频繁创建连接、发 SQL、发 RPC？ |
| 资源释放 | 连接/流是否使用 try/finally 或明确 close/dispose？ |
| 异步与 Promise | 是否正确使用 async/await、避免未处理的 Promise rejection？ |

### 2.6 安全相关编码

| 检查项 | 说明 |
|--------|------|
| SQL/查询安全 | 查询构造是否使用参数绑定，禁止字符串拼接拼 SQL/NoSQL 查询？ |
| 日志不输出敏感信息 | 是否禁止在日志中输出密码、token、隐私数据？ |
| 外部输入校验 | 对外部输入（HTTP 参数、消息体）是否做类型与范围校验？ |
| 依赖与漏洞 | 是否定期关注依赖版本与已知漏洞（如 npm audit）？ |

### 2.7 并发与共享状态

| 检查项 | 说明 |
|--------|------|
| 单线程与异步 | 是否理解 Node 单线程事件循环，避免全局可变状态在并发请求下竞态？ |
| 锁与队列 | 如需分布式锁或任务队列，是否选用成熟方案并配置超时与重试？ |

### 2.8 编码风格与复杂度

| 检查项 | 说明 |
|--------|------|
| 统一风格 | 是否遵循 ESLint/Prettier 或团队约定？ |
| 方法/模块复杂度 | 是否控制函数长度、模块职责单一，避免过长函数与上帝模块？ |

---

## 三、输出格式建议

评审或 Code Review 时，**每个维度/每条检查项必须给出结论**，不能只罗列问题。建议格式：**维度** → **现状** → **结论**（满足/不满足/风险）→ **建议**。
