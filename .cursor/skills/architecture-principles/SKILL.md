# 技术架构原则

## 核心原则（请按团队实际替换）

1. **简单优于复杂**：在满足需求的前提下优先简单方案，避免过度设计。
2. **边界清晰**：模块/服务职责单一，依赖方向明确，避免循环依赖。
3. **可观测**：关键路径有日志、指标或追踪，便于排障与容量规划。
4. **可演进**：预留扩展点或兼容策略，避免一次性大爆炸式改造。
5. **安全与合规**：数据与接口符合安全与合规要求（认证、鉴权、敏感数据脱敏等）。

## 评审检查清单

- [ ] **背景与约束**：方案是否写清背景、目标及约束（性能、可用性、合规）？
- [ ] **职责与边界**：核心组件/服务职责是否单一？边界是否明确、依赖方向是否清晰、无循环依赖？
- [ ] **依赖与调用链**：依赖关系与调用链是否画出或列出？是否标注数据流向？
- [ ] **技术选型**：选型理由是否充分？是否有替代方案对比或说明不选理由？
- [ ] **接口/契约**：接口或契约是否稳定？版本策略（兼容、废弃）是否明确？
- [ ] **可观测性**：日志、监控、告警是否覆盖关键路径？是否便于排障与容量规划？
- [ ] **风险与回滚**：是否列出主要风险与回滚/降级策略？

## 产出物建议

- **技术方案**：背景、目标、架构图、核心模块说明、接口与数据流、选型理由、风险与回滚。
- **ADR**：背景、决策、后果；可放在 `references/adr-templates.md` 供引用。

## 工作结束后的默认动作

- **提交 GitHub**：任务或迭代完成后，默认执行或明确建议用户执行「提交到 GitHub」（`git add` → `git commit` → `git push`），避免工作结束未提交导致无法回滚；commit 信息需清晰、可与需求/任务关联。

## 使用说明

- 本 Skill 可被 **role-architect** 引用：角色 Agent 先遵循本原则与检查清单，再按任务产出技术方案或评审结论。
- 单独做技术方案/架构评审时，Agent 可直接匹配本 Skill；写技术方案或 ADR 时建议与 role-architect 串联使用。
