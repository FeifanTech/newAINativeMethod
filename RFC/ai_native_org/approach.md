# 组织 AI-Native：思路与方案综合文档

> 本文档在现有 RFC（ai_native_org.md 愿景、next_step.md 分层与可行性）基础上，整理出一套可对内对外对齐的「组织 AI-native」思路与落地方案，供讨论与执行参考。

---

## 一、组织 AI-Native 的定义

**一句话**：组织 AI-native = 把组织的 **输入 → 状态 → 输出** 尽量变成 **可读、可写、可被 AI 消费** 的「记忆 + 能力 + 护栏」，而不是只靠人脑和会议。

- **输入**：需求、市场信号、客户反馈、指标、政策等。
- **状态**：策略、OKR、架构、项目记忆（decisions / tasks / changelog）、团队技能与文化等。
- **输出**：产品、服务、发布、运营动作、对外沟通等。

「可编程」在此的含义是：这些输入、状态、输出有 **稳定结构**（如 memory/、docs/、Skills），AI 能 **读得到、写得上、被约束得住**，人则做 **确认、裁决、例外**。当前基线仓在「工程这条链」上，先把 **状态**（原则、决策、任务、changelog）和 **能力**（Skills）做成可编程的。

因此，组织 AI-native 的思路是：把同一套「记忆层 + 能力层 + 基线约定 + 护栏」从 **单项目** 逐步扩展到 **多项目 → 团队 → 组织**，而不是另起一套新哲学。

---

## 二、分层思路：从工程基座到组织操作系统

将组织 AI-native 拆成 **六层**（第 0 层为基座，第 1～6 层由近及远、由易到难）：

---

### 第 0 层：工程基座（已有基础）

- **内容**：基线仓 + Skills + memory 约定 + 采纳指南 + 企业级检查清单（Java / Python / TS）+ sync-skills、release-notes、decisions-summary、doc-reflector 等。
- **作用**：单项目内「原则可执行、决策可追溯、任务可沉淀、发布可说明」，且 **格式统一**，为后续「多项目聚合」打基础。
- **组织意义**：组织 AI-native 的 **契约层** —— 所有上层能力（Hub、角色 Copilot、会议落盘）都假定项目遵守这套约定；没有这一层，上层难以成立。

**建议**：持续做两件事——**约定稳定**（memory/、docs 结构不随意变）、**可验收**（用「AI-native 就绪度」清单判断项目是否达标）。若建设 Org Hub，就绪度即「哪些项目有资格被索引」的准入门槛。

---

### 第 1 层：多项目复制与就绪度

- **内容**：用现有基线 + 采纳指南，将 AI-native 基座复制到更多项目；并定义 **项目级就绪度**（例如：具备 .cursor/skills、memory/、README 中「我们怎么用 AI」一节、实际使用过 PRD/架构/实现/发布类 Skill）。
- **组织动作**：选 3～5 个关键项目做 **深度示范**（配小教练、按清单跑通、记录顺/阻点），把结果反哺基线仓（case-study 或 checklist 迭代），再推广到更多项目。
- **边界**：不急于上「组织级系统」，先把「多少项目真正按同一套约定在跑」做扎实。

**结论**：组织 AI-native 的 **真实起点** 是「有多少项目已经 AI-native」，而不是「有没有一个炫的 Org 平台」。本层核心是：**就绪度定义 + 示范项目 + 可复制的接入故事**。

---

### 第 2 层：组织级记忆中枢（Org Memory Hub）

- **内容**：一个 **只读聚合视图**，将「已接入基线且符合约定」的项目的 memory/ 与关键 docs（PRD、架构、Release Notes）定期抽取、索引，支持按项目/时间/主题查询。
- **典型问题**：「最近一季所有项目里与『幂等』『重试』『溯源』相关的决策有哪些？」「哪些项目在做溯源/存证类需求，PRD 与方案在哪？」「最近 N 个版本的 Release Notes 摘要？」
- **实现思路**：约定各项目 memory/ 与 docs 的 **命名与结构**（与基线仓一致）→ 轻量 **indexer**（定时拉仓或接 API，解析 md）→ 存成「文档表 + 标签」或简单向量索引 → 提供 **Org Copilot** 或 Chat 项目读该索引，用 preset 问法或自然语言提问。
- **边界**：不追求一上来就「大而全的知识图谱」；不做写入（Hub 只读，写仍在各项目 memory/）。

**结论**：Hub 的 **数据契约** 就是第 0 层定义的 memory/ 与 docs 结构；基线仓是「Hub 的 schema 拥有者」。先让 3～5 个示范项目进 Hub，能回答 5～10 个 preset 问题，再谈扩展与自然语言泛化。

---

### 第 3 层：角色 Copilot（从「工具」到「角色视角」）

- **内容**：同一份 Hub 数据，按 **角色** 呈现不同视图——例如项目负责人看「迭代进度 + 最近决策 + Release Notes + 风险」，架构看「最近 ADR + 跨项目冲突/重复」，产品看「PRD 清单 + 需求评审结论 + 即将发版功能」。
- **实现思路**：先 **无 UI** —— 在现有 Org Copilot 中按角色做 **preset 指令**（如「你是 X 团队 TL，根据 Hub 数据生成过去一周关键变化的一页周报」），背后用 Hub；跑顺后再把常用问题「按钮化」成简单 Web 面板。
- **优先级**：先做 **一个角色**（如项目 Owner / TL），把「进度 + 决策 + 发布 + 风险」这条线打穿，再复制到产品/架构。

**结论**：角色 Copilot 的价值不在于「多一个聊天界面」，而在于让「TL/PM/架构师每周必看的东西」变成 **一次提问或一次点击** 就能拿到，从而倒逼下面两层（项目真的在用 memory/、Hub 真的有数据）。关键是：**选准一个角色、摸清他真正关心的 3～5 个问题**，做深做透。

---

### 第 4 层：会议 / 群聊 / 决策写入记忆

- **内容**：将「会议结论、行动项、重要群聊中的决策」 **按规则落盘** 到对应项目的 memory/（decisions.md Proposed、tasks.md Planned、changelog.md），而不是只留在会议纪要或聊天记录里。
- **会议**：会中/会后用 AI 做摘要 → 抽取决策与行动项 → 生成「建议写入 memory/ 的条目」→ **人确认后** 写入对应项目（或由集成脚本写入）。
- **群聊**：对关键群做「只读旁听」→ 识别「像决策/像任务」的消息 → 提示负责人「是否写入 memory/」→ 人点确认后落盘；可顺带做「高频问答 → FAQ/周报」。
- **原则**：**AI 建议，人确认**；写到哪里、写什么格式，完全遵循第 0 层的 memory 约定，不另造一套「会议记忆」。

**结论**：本层 **瓶颈** 在习惯与权责——大家是否接受「决策和任务以 memory/ 为准」；谁有权确认「这条算决策、这条算任务」。建议先选 1～2 类会议（如需求评审、设计评审）试点，明确「谁在会后负责确认并落盘」，再考虑群聊；技术反而不是主战场。

---

### 第 5 层：策略 / OKR / 投资组合（信息聚合 + 一致性检查）

- **内容**：用 Hub 中的项目历史、Release、决策，结合高层指标与外部信息，做两件事——**会前** 生成「策略/OKR 背景包」；**草案后** 做「OKR 与项目/北极星的一致性检查」。不替代人定战略，只做 **信息聚合 + 矛盾发现**。
- **进阶**：当 Hub 数据足够多且干净，可做「投资组合级」分析：哪类项目 ROI 高、哪些技术路线反复踩坑、哪些团队交付稳，供高层做投入/收尾/平台化决策。
- **原则**：AI 是 **策略助手 + 一致性审查**，不是决策主体；敏感数据（财务、用户）的边界与权限需事先界定。

**结论**：本层适合作为「Hub + 角色 Copilot 用顺之后」的增强，而非第一波主战场。先解决「决策与项目信息是否被结构化沉淀」，再谈「用这些信息辅助战略」。

---

### 第 6 层：多 Agent 组织（长期愿景）

- **内容**：组织被建模成「多角色 Agent + 流程 Agent」的协作网络——每个角色有对应 Agent 配置（职责、边界、常用 Skills），每条关键流程既有人的 swimlane 也有 Agent 的 swimlane；Agent 做固定动作（找文档、做 checklist、生成草稿、初筛），人做 trade-off、例外与拍板。
- **与当前基线仓的关系**：现有 role-architect / role-developer / role-product-designer 与职能型 Skills，已是 **单项目内多角色/多能力** 的雏形；组织级多 Agent 则是「跨项目 + 流程编排（orchestrator）+ 权限与审计」的扩展。
- **落地节奏**：短期不做「全组织多 Agent」，只选 **一条端到端流程**（如某内部工具「从需求到发布」）做「多 Agent 版」试点，每步保留人工确认，跑通再考虑推广。

**结论**：多 Agent 组织是 **方向**，不是第一年目标。先把第 0～3 层做稳（基座 + 多项目复制 + Hub + 一个角色 Copilot），再谈流程级编排与多 Agent。

## 三、组织 AI-Native 的几条原则

1. **契约优先**  
   组织级能力（Hub、角色 Copilot、会议落盘）都建立在「项目遵守同一套 memory/ 与 docs 约定」之上。基线仓的核心价值，就是 **定义并维护这套契约**。

2. **记忆层是底座**  
   没有稳定、可被索引的「组织记忆」（项目级 memory/ + 聚合后的 Hub），角色 Copilot 与策略辅助都是空壳。因此优先把「项目是否按约定写 memory/」和「Hub 是否能把它们收上来」做扎实。

3. **角色视角优于工具堆砌**  
   与其堆很多「写 PRD Copilot」「写代码 Copilot」，不如先做好「项目负责人一周要看的 5 件事」「架构师要看的 ADR 与冲突」——用角色视角倒逼数据与流程被规范使用。

4. **AI 建议，人确认**  
   写入 memory/、写入 decisions、生成 Release Notes，都保持「AI 产出草稿或建议，人确认后落盘」。既保留审计与权责，又避免「AI 乱写」带来的信任崩塌。

5. **度量为证，但不强求一步到位**  
   交付 lead time、PR/文档完成时间、决策与 changelog 覆盖度、Skills 使用分布等，可逐步纳入「AI-native 健康度」；先在小范围试点采集，再谈全组织仪表盘。

---

## 四、方案表述（对内对外一句话版）

- **愿景**：把组织建成「可编程的输入–状态–输出系统」，记忆可沉淀、能力可复用、护栏可落地。
- **基座**：工程层基线仓（Skills + memory 约定 + 采纳指南 + 企业级检查清单 + sync/release/decisions/doc-reflector 等），作为 **全组织 AI-native 的契约与能力来源**。
- **路径**：第 1 层多项目复制与就绪度 → 第 2 层 Org Memory Hub → 第 3 层角色 Copilot（先一个角色）→ 第 4 层会议/群聊落盘 memory/ → 第 5 层策略/OKR 辅助 → 第 6 层多 Agent 长期演进。
- **原则**：契约优先、记忆为底座、角色视角、AI 建议人确认、度量渐进。

## 六、商机获取的 AI-Native 化（基于 chance.md）

> chance.md 记录了「把找机会做成 AI-native 流水线」的头脑风暴：从洞察 → 点子 → 验证 → 放大，并给出了「机会雷达」的第一版实施方案。本节对其做可行性分析，并把结论与落地方案纳入本综合文档。

### 6.1 chance.md 内容摘要

- **定位**：在「已知业务里的 AI-native 研发与组织运转」之外，把 **发现与验证新商业机会** 也做成可编程、有节奏的组织能力。
- **五层设想**：
  1. **机会雷达**：AI 定期扫行业/政策/平台/竞品/开源，结合自我画像做「我们 vs 世界」缺口分析，产出趋势 + 机会候选。
  2. **场景化痛点挖掘**：AI 拆解目标角色的一日工作流，结合公开数据（评论、论坛、招聘 JD）挖痛点，筛出可自动化/可增强的点。
  3. **点子→MVP 验证流水线**：标准化「机会描述 → 市场扫描 → MVP 方案 → 验证渠道设计」，AI 做模板与草稿，人拍板；MVP 物料（落地页、demo、话术）大量由 AI 生成。
  4. **渠道侧 AI**：多版本内容（长文/短视频/种草话术/老板 PPT）+ 投放分析，用 AI 做叙事与渠道的 A/B 测试；借平台 AI 生态（如 1688）当渠道与用户研究工具。
  5. **机制层**：机会流写入 memory/（如 opportunities.md）、机会小实验的预算与评审、晋升/OKR 中纳入「新机会发现与验证」。
- **第一版落地重点**：固定节奏（如双周）的「机会雷达」—— 固定信息源、固定 Prompt 流程、机会卡模板、人工评审后写入 org-level 机会库（opportunities.md 或独立仓库）。

### 6.2 可行性分析

| 维度 | 结论 | 说明 |
|------|------|------|
| **与现有契约的兼容性** | ✅ 高 | 机会卡与机会库可完全遵循第 0 层约定：固定模板、固定路径（如 `memory/opportunities.md` 或 `docs/opportunities/`），AI 产出草稿、人确认后落盘，符合「AI 建议、人确认」原则。 |
| **对基座的依赖** | ✅ 低 | 机会雷达与机会库不依赖 Hub 或角色 Copilot；只需「一个 Org 级工作区 + 模板 + Prompt + 人工评审」。可先于第 2～3 层独立跑。 |
| **机会雷达（双周简报）** | ✅ 高 | 信息源可先人工/半自动（URL 清单 + 搜索 + 粘贴），AI 做聚类与机会卡草稿；流程、模板、节奏在 chance.md 中已具可执行性。主要风险在「谁持续维护信息源」和「谁稳定参加评审」，属组织习惯而非技术。 |
| **场景化痛点挖掘** | ⚠️ 中 | 思路清晰，但依赖「目标角色与赛道」先收敛；适合作为「机会雷达筛出方向后」的第二步，用同一套能力画像 + 文档模板 + Skills 做深挖。数据获取（爬虫/合规）需单独评估。 |
| **点子→MVP 验证流水线** | ⚠️ 中 | 模板化 + AI 草稿可行；真正降本的是「MVP 物料 80% AI 生成」。与基线仓的「PRD/架构/发布」Skills 天然衔接——同一套可编程能力可复用到「机会验证」这条线。建议先跑通 1～2 个机会的完整验证再固化流程。 |
| **渠道侧 AI** | ⚠️ 中 | 多版本内容与简单分析可行；「骑平台大船」取决于商务与产品定位，非纯技术。可列为「机会验证通过后」的放大动作，不必作为第一波。 |
| **机制层（机会入 memory、预算、OKR）** | ✅ 高 | 与现有「记忆层是底座」「契约优先」一致。opportunities.md 或独立机会库即「组织记忆」在商机维度的扩展；小实验预算与评审、OKR 权重属于制度设计，不依赖复杂系统。 |

**总体判断**：chance.md 中的链路 **整体可行**，且与现有六层不冲突。**优先可落地**的是：机会雷达（固定节奏 + 机会卡模板 + 人工评审）+ **机会流写入 memory/**；场景挖掘与验证流水线可作为「雷达产出机会后的下一步」逐步接入；渠道与机制层可后置或与第 5 层（策略/OKR）协同。

### 6.3 与现有分层的关系

- **第 0 层**：机会卡模板、opportunities 的路径与格式（如 `memory/opportunities.md` 或 `docs/opportunities/YYYY-MM-机会雷达.md`）纳入 **契约**，与 decisions/tasks/changelog 并列，同属「组织状态」的可编程部分。
- **第 1 层**：若采用「org-level 机会库」（独立仓库或 Notion/飞书），可与多项目就绪度并行；不要求所有项目都写 opportunities，但要求 **至少有一个组织级机会记忆** 且结构稳定。
- **第 2～3 层**：Hub 与角色 Copilot 成熟后，可把机会库纳入索引与视图——例如「本月机会清单」「长期未推进机会」「已转项目的机会」成为 TL/管理层 Copilot 的 preset 问题。
- **第 5 层**：策略/OKR 背景包可包含「机会雷达摘要」与「机会→项目转化率」；机会探索的预算与 OKR 权重即本层在「商机」维度的体现。

因此：**商机获取不是新的一层，而是「输入侧」的扩展**——把「市场信号、痛点、机会假设」也做成可读、可写、可被 AI 消费的记忆与流程，与现有「状态（项目记忆）→ 输出（发布、决策）」形成闭环。

### 6.4 落地方案摘要

1. **短期（0～2 个月）**
   - 在基线仓或 org 文档中 **定义机会卡模板** 与 **机会库路径**（如 `docs/opportunities/` + `opportunities.md` 汇总表）。
   - 确定「机会雷达」的 **固定节奏**（建议双周）、**主赛道范围**（1～3 个）、**能力画像**（一页纸）。
   - 跑通 **第一轮机会雷达**：固定信息源清单 → Prompt A（趋势+案例）→ Prompt B（机会卡草稿）→ 人工评审（30～60 分钟）→ 写入机会库；迭代一次模板与 Prompt。
   - 明确 **谁负责** 维护信息源、谁参加评审、谁负责把「选定机会」推进到下一步（桌面调研 / 小规模访谈 / 转项目）。

2. **中期（3～6 个月）**
   - 对雷达筛出的 1～2 条机会，走 **场景化痛点挖掘**（角色工作流拆解 + 公开数据聚类），产出更细的机会卡或需求假设。
   - 对 1 条机会走通 **点子→MVP 验证流水线**：机会描述 → 市场扫描 → MVP 方案 → 验证渠道设计 → 落地页/demo/话术（尽量用现有 Skills + AI 生成），并复盘流程是否可模板化。
   - 若已有 Hub/角色 Copilot，把 **机会库纳入查询**（preset 问题：未推进/已转项目/按赛道汇总）。

3. **长期（与第 5～6 层协同）**
   - 机会小实验的 **预算与评审机制** 固化；晋升/OKR 中明确「新机会发现与验证」的权重与表述。
   - 策略会前背景包中纳入「机会雷达摘要」与「机会→项目转化」；必要时做「投资组合」视角（哪些机会在试、哪些已关、哪些转项目）。

### 6.5 原则对齐

- **契约优先**：机会卡格式与机会库路径一经确定，全组织统一，AI 与人都按同一套写。
- **记忆层是底座**：机会流与项目流一样，写入 memory/ 或约定好的 docs，可被索引、可被追问、可做「长期未推进」等分析。
- **AI 建议，人确认**：趋势报告与机会卡均为 AI 草稿，优先级与「是否进入验证」由人拍板。
- **度量为证、渐进**：先不追求「机会转化率」仪表盘，先做到「每双周有稳定产出 + 机会有状态可查」，再谈指标。
